# 정원 웨딩 비율·배치 재설계

- 날짜: 2026-10-17
- 상태: 레퍼런스 조사와 설계 완료. 실제 게임/PNG에는 미반영.
- 기준 커밋: 821d793 (변형 모션 제거, 하객 속도 48px/s)
- 비교 보드: `tools/garden-design-review.html`
- 재현 계산: `node tools/probe-garden-design.mjs` → `tools/garden-design-layouts.json`

## 1. 결론

메인의 벚꽃나무를 **96×128 프레임, 실제 그림 96×96~104px**로 새로 제작한다. 지금의 64×96 프레임 안 실제 그림은 64×64px로, 실제 높이 약60px인 하객과 거의 같다. 따라서 단순 꽃관목처럼 보인다. 목표는 나무의 실제 높이를 하객의 약1.6~1.7배로 만드는 것이다.

넓어진 수관에 맞춰 나무를 위로 한 줄 올리고 케이크·조명을 리셉션 구역으로 묶는다. 중앙 96px 길, 352px 맵 폭, 32px 이동 격자, 128px 잔디 재질, 최근 모션 안정화는 유지한다. 나무 확대를 위해 맵이나 카메라 전체를 확대하지 않는다.

이 문서의 픽셀 수치는 아래 레퍼런스와 현재 프로젝트 측정을 바탕으로 제안한 **이 프로젝트의 설계값**이다. 외부 제품의 권장 규격을 그대로 옮긴 것이 아니다.

## 4. 나무 에셋 설계

### 메인용 대형 벚꽃나무

| 항목 | 목표 |
|---|---|
| 출력 프레임 | 96×128 RGBA |
| 실제 그림 | 폭88~96px, 높이96~104px. 검토 보드는 기존 그림의 실제96×96 비율로 모형화했다. |
| 색/화풍 | 아이보리·연분홍 꽃, 일부 세이지 잎, 보이는 갈색 가지. 그림 전체의 어두운 윤곽은 최종 해상도1px 기준으로 유지. |
| 형태 | 둥근 꽃구름 하나가 아니라 높이가 다른 수관3~4덩어리와 분기된 줄기. 왼쪽/오른쪽 변형은 우선 반전으로 비교 후 판단. |
| 발 기준 | 최종 프레임 하단. 중앙 줄기의 접지점은 이미지 폭 중앙. |
| 충돌 | 줄기 주변32×32 기본안. 수관 폭96px 전부를 벽으로 만들지 않는다. |
| 출력/등록 | `tree-large-cherry-v1.png` 등 별도 이름/ID 권장. 기존 tree ID를 무조건 덮어쓰지 않고 방명록 배치까지 함께 검토한다. |

보드의 확대 PNG는 **비율 비교용**이다. 기존64px 그림을 런타임에서1.5배 늘리는 것을 최종안으로 삼지 않는다. 새 크기에서 꽃 머리와 줄기·외곽선의 픽셀 밀도를 다시 맞춘다.

### 가림과 탭 처리

- 줄기 충돌은 위치/너비를 명시하는 별도 footprint 필드로 표현한다. 이미지 프레임에서 자동 추론한 값은 기존 소품의 기본값으로 남긴다.
- 하객 초기 배치와 배회는 큰 수관 바로 뒤에서 얼굴이 가려지지 않도록 시각적 예약 영역을 사용한다. 줄기 충돌과 같은 값으로 쓰지 않는다.
- 플레이어가 수관 뒤로 들어가는 경우를 별도로 검사한다. 먼저 이름/위치 표식이 보이는지 확인하고, 필요할 때만 해당 수관의 가림을 줄이는 방식을 적용한다. 모든 나무를 계속 반투명하게 만들거나 하객마다 깜빡이게 하지 않는다.
- 큰 수관의 투명 여백을 탭해도 나무가 다른 사람의 탭을 가로채지 않도록 비상호작용 장식의 hit 영역을 검토한다.

### 기존 엔진으로 계산한 공간 영향

`node tools/probe-garden-design.mjs`로 현재 PNG 크기와 객체 예약 규칙을 사용했다. 인원은 30개의 서로 다른 방문 데이터를 입력했을 때 보이는 광장 인물 수이며, 메시지 목록의 데이터 수와 다르다.

| 모형 | 기본 분위기 하객 | 30명 입력 표시 수 | 네 방 접근 |
|---|---:|---:|---|
| 현재64×96·5행 | 10 | 18 | 모두 가능 |
| 96×128·3행, 나무만 교체 | 10 | 18 | 모두 가능. 다만 케이크와 수관이 시각적으로 겹쳐 그대로 적용 불가. |
| **96×128·3행 + 케이크9행/왼 조명7행** | **10** | **17** | **모두 가능** |
| 96×128·4행 | 10 | 16 | 모두 가능 |
| 96×128·5행 | 10 | 14 | 모두 가능. 아래쪽 하객 구역을 너무 많이 차지한다. |
| 128×160·3행 | 10 | 16 | 길은 열리지만 꽃과 인물을 덮어 권장하지 않는다. |

줄기 충돌/시각 예약을 분리한 뒤에는 수용 인원을 다시 계산해야 한다. 위 수치는 새 충돌 구현의 결과가 아니다. 최소10명은 유지하고, 표시하지 못한 방문객도 메시지 목록에서는 계속 볼 수 있어야 한다.

### 방명록은 별도 조정

동일 나무 ID의 파일만 크게 갈아끼우지 않는다. 방명록은 우체통과 신부 위치가 다르다. 대형 나무 후보는 왼쪽0열/오른쪽8열·0행, 발128px를 기준으로 검토한다. 우체통 중앙과 신부 얼굴을 비우고, 하드코딩된 RESERVED의 옛 나무 범위를 새 배치의 그림/충돌 정보로 계산하도록 정리한다. 편지 수에 따른 꽃 표시 영역과 출구 경로는 별도 검증한다. 이 방 배치는 아직 계산/게임 검증 전 후보안이다.

## 6. 함께 개선할 화면/미술 항목

### P1: 메인 안내 카드와 첫 구도

- 메인에서는 기본 안내 카드를72~80px 목표로 축약한다. 제목·짧은 안내·축하 수만 우선 표시하고 산책 안내/기기 저장 설명은 펼치거나 별도 안내로 이동한다. 빠른 메뉴와 접근 가능한 설명은 유지한다.
- 장식이 보이는 영역이 약70~80px 늘어나므로 리셉션 공간을 더 잘 볼 수 있다. 정확한 이득은320/390px 화면에서 최종 문구로 다시 측정한다.
- 첫 입장은 아치·커플·두 나무를 한 화면에 잡는 고정 구도로 시작한다. HUD 아래12px 이상 여백을 두고, 캐릭터 이동 전에는 카메라가 미세하게 재중앙화되지 않게 한다.
- 이동 중에는 안전 영역을 벗어날 때만 따라가는 방식을 검토한다. 기존 양옆 잔디의 카메라 위상/배율 동기화는 회귀시키지 않는다. 나무 크기에 맞춘 자동 줌은 넣지 않는다.

### P2: 꽃과 리셉션의 시각적 우선순위

- 꽃은 현재 수국/장미의 조합을 유지한다. 나무 확대 후에도 단상과 꽃 아치가 주인공인지 먼저 판단한다.
- 상단은 나무·아치·단상, 중간은 하객과 테이블, 하단은 공간 입구로 역할을 나눈다. 장식을 더 늘리기 전에 같은 역할의 소품을 묶는다.
- 필요하면 단상 가까운 꽃 군집만 높이/밀도를 조금 키우고 아래쪽은 간격을 둔다. 꽃 머리는320px 화면에서 최소5~6px로 구분돼야 하며, 작은 들꽃을 다시 촘촘한 반복 무늬로 만들지 않는다.
- 잔디 v5의128px 연속 재질과8색 저대비는 유지한다. 수관 아래 그림자를 추가한다면 나무에 포함된 정적 그림자로 만들고 모든 소품에 같은 광원 규칙을 쓴다.
- 캐릭터 PNG 전체 늘림·기울임·주기적 대기 흔들림은 재도입하지 않는다. 실제 보행 프레임 제작은 별도 작업으로 다루며 현재 안정된 모션에 덧씌우지 않는다.

## 7. 구현 순서와 완료 조건

1. **구조**: footprint/시각 예약 영역을 구분하고 나무 크기/발 좌표를 데이터로 명시한다. 기존 소품과 문 경로가 유지되는지 검사한다.
2. **대형 나무 한 쌍**: 96×128 최종 PNG를 새로 제작하고 기존 나무를 보존한다. 실제 bbox·픽셀 밀도·320px 인물 가림을 확인한다.
3. **메인 배치**: 나무3행, 케이크9행, 왼 조명7행을 적용하고 기본10명·30명 입력·배회 상태를 확인한다. 초기/이동 중/최대 인원 모두 검사한다.
4. **메인 카드와 카메라**: 기본 카드 높이 축약, 첫 구도, 카메라 안전 영역을 순서대로 확인한다. 모션 줄이기 환경을 포함해 경계 흔들림을 다시 검사한다.
5. **방명록**: 별도 배치안으로 우체통·신부·꽃 메시지·출구를 확인한 뒤 대형 나무를 적용한다.
6. **마지막 미술 조정**: 위 항목이 안정된 뒤에만 꽃 군집/그림자 밀도를 조정한다.

완료 판정은390×844와320×740 화면에서 한다. 커플 두 얼굴, 두 나무의 접지점, 첫 꽃장식이 확인돼야 한다. 빈 길96px, 네 방 접근, 하객10명, 메시지 탭과 선택 가능성을 유지한다. 야외→실내→야외 전환에서 잔디 경계 정렬을 확인한다.

이번 요청에서는 조사·설계·비교 보드만 작성했다. 런타임 JS/CSS와 실제 PNG/manifest는 바꾸지 않았다. API 연결과 실사진은 기존 마지막 단계 보류를 유지한다.
